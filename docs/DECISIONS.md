# Decisions

Lightweight ADR log. Status: **Accepted** unless noted. Newest decisions append at the end.

## D-001 Monorepo with `backend/`, `frontend/`, `docs/`
One repo keeps the API contract, schema mirrors and docs in lockstep. No workspace tool (npm workspaces, turborepo, make) yet — two independent toolchains with documented commands are enough.

## D-002 Observations are immutable, append-only, with client-generated UUIDs
Makes offline creation and retried sync idempotent and removes merge logic. Corrections use `supersedes`. Trade-off: storage grows; "current value" queries must follow `supersedes` chains (not implemented yet).

## D-003 Mandatory provenance with three origins
`simulated | measured | modeled`, with origin-specific required fields enforced in `Provenance`. Summaries partition by origin; derived values are always `modeled` and name their input origin.

## D-004 Descriptive only: no diagnosis, no clinical thresholds
Metric definitions carry only physical-plausibility rules. Any future limit/reference range must be an injected object with a mandatory citation. A test asserts `MetricDefinition` has no threshold fields.

## D-005 Pure calculations, separate from schema and presentation
`calculations.py` (arrays in, numbers out) ← `service.py` (observations → summary) ← API ← UI. Enforced by AST tests.

## D-006 PostgreSQL: architecture now, implementation later
Delivered: `ObservationRepository` protocol, in-memory reference implementation, reviewed `schema.sql`, config switch, compose file. Not delivered: a working Postgres repository, because no PostgreSQL/Docker was available to test it and an untested persistence layer is worse than an honest skeleton. Migrations tooling deferred until the schema stabilises.

## D-007 Raw IndexedDB wrapper instead of `idb`/Dexie
Three stores and ~10 operations; ~100 lines avoids a dependency. Revisit if queries grow complex.

## D-008 Frontend types mirrored by hand; OpenAPI committed and drift-tested
Avoids a codegen toolchain at this stage. `docs/api/openapi.json` is regenerated by script and a test fails if stale. Risk: TS mirrors can drift from the backend — adopt codegen (e.g. `openapi-typescript`) if drift appears.

## D-009 Tailwind CSS v4 via the Vite plugin
No `tailwind.config` / PostCSS config needed; `@import "tailwindcss"` only.

## D-010 Sync protocol: idempotent push + monotonic-cursor pull; no last-writer-wins
Per-item results so one bad record cannot fail a batch; client isolates HTTP-422 poison records by single-item retry; rejected items are quarantined, not retried forever.

## D-011 Health modules are plugins to a registry; one composition root
Each module exposes a `HealthModuleSpec`; `registry.py` is the only importer of all four. Adding a module touches core enum, registry, frontend list, tests, docs.

## D-012 scikit-learn used narrowly
Only `RobustScaler` (behavioral baseline deviation) today. It stays a declared dependency because the project requires ML capability, but no model training exists or is claimed.

## D-013 No authentication/authorisation in v0.1
Acceptable only because no real data exists and the API is local. Must be designed before any real or sensitive data: authn/z, per-subject access control, audit log, encryption in transit and at rest.

## D-014 Tooling: pip + venv, npm
`pyproject.toml` with `[dev]` and `[postgres]` extras; `package-lock.json` committed. No poetry/uv/pnpm to keep prerequisites minimal.

## D-015 Version pins follow the registry at build time
`package.json` uses caret ranges of versions current on 2026-11-13 (Vite 8, Vitest 5, TypeScript 7, Tailwind 4.3, React 19.3). Python uses lower bounds only; installed: see `pip list`. Add a lock/constraints file before CI or release.

## D-016 Telemetry contract adopted (partially implements proposal P-1)
The briefing's 11-field event (`event_id, device_id, crew_id, timestamp, domain, indicator, value, unit, source, quality, synthetic`) is the gateway wire contract (`core/telemetry.py`). Three **optional** extension fields carry provenance the storage model requires: `generator_version` + `seed` (required when `synthetic: true`) and `source_ref` (required when `synthetic: false`). The gateway maps each event to a `HealthObservation` (new fields `device_id`, `quality`); `crew_id → subject_id`, `domain → module`, `indicator → metric` (`<domain>.<indicator>`), `timestamp → observed_at`. `synthetic` stays derived from `provenance.data_origin`. Units: wire aliases such as `bpm` are rewritten to the canonical unit (identity conversion only). `quality` ∈ valid/suspect/invalid is a **provisional vocabulary** — non-valid events are stored and shown, never dropped. Events are validated one by one: a bad event is recorded in the rejection audit log (reason + raw payload) and never blocks the batch. New metrics: `cardiovascular.heart_rate`, `radiation.dose_rate`, `bone.countermeasure_exercise_duration` (activity logging only; a wearable does not measure bone density). Dose rates are summarised descriptively and never summed. **Not yet done:** accumulated exposure from dose rate, the Normal/Watch/Warning/Critical alert layer (needs sourced thresholds, P-2), ground sync.

## D-017 SQLite as the gateway's local store
Stdlib `sqlite3` (no new dependency; runs on a Raspberry Pi), WAL mode, append-only triggers, same repository contract as the in-memory store (contract tests run against both). PostgreSQL stays the intended ground/cloud store (D-006). Device-side buffering is in memory only: it survives a gateway outage, not a device-process restart.

## D-018 Cross-domain analysis engine as `medvital/analysis/` (not a health module)
Descriptive stats, personal-baseline deviation, missingness/data-quality and statistical anomaly flags live in a peer package
of `simulation/`, importing only `medvital.core`. It is not a `ModuleId`: it serves all four domains, so making it a module would
break rule 5. Pure arithmetic in `analysis/calculations.py`; dependency rules in `tests/test_analysis_architecture.py`. No new
dependency (NumPy/pandas already declared). It reads `quality` and `device_id` (D-016) directly: quality filters
what enters statistics (default `valid` only), device splits series. Numbered D-018 because D-016/D-017 were assigned on the telemetry branch; the two were developed in separate checkouts and merged. Not yet
exposed through the API (a route ⇒ OpenAPI regeneration + frontend mirror). Method: SCIENTIFIC_METHODOLOGY §9.

## D-019 Published research values are `PublishedReference` records, not observations (decided 2026-11-14)
`DataOrigin` stays exactly `simulated | measured | modeled` (rule 2, D-003 unchanged). A value taken from a publication
(a cohort mean, a reported rate, a reference interval) is a separate, read-only record and **never** a `HealthObservation`,
so a cohort average can never appear as an individual astronaut's reading.

Planned fields (implementation not started; tracked in MODELING_GAP_ANALYSIS G-13):
`reference_id` (`REF-` + stable slug, e.g. `REF-SIBONGA2007-…`), `citation` (required; authors, title, venue, year),
`source_identifier` (required; DOI, PMID, NTRS id or dataset accession), `verification` (`verified_at_source` |
`unverified`, plus who/when), `quantity` and `unit` (canonical, as for metrics), `value` and/or `interval`, `statistic`
(mean, median, SD, …), `population` (n, species, cohort, mission type), `context` (site, method, posture, timepoint),
`limitations` (required free text), `retrieved_at`.

Rules: a reference may be *displayed beside* an individual's series and used as a *configured, cited assumption* in a
modeled trajectory (the modeled value's provenance then names the `REF-` id); it is never pooled into, averaged with, or
stored as observations, and it never becomes a clinical threshold unless rule 3 is explicitly changed. Unverified
references may be stored but must render as unverified.

## D-020 Measurement schedules are stored plans with a mission-relative time model (M2)
A `MeasurementSchedule` (`core/schedule.py`) records *when* a metric is planned to be measured, by which method, for which
subject, and where the plan came from (`basis`: `protocol` requires `source_ref`; `simulated` is an arbitrary test plan).
Times are NASA-style offsets from mission anchors (`L-13`, `R+1`; single or recurring), resolved only when launch and
return times are supplied; resolved times are *modeled*. Schedules are immutable and append-only with `supersedes`
revisions, stored by the memory and SQLite repositories (additive SQLite table with append-only triggers; PostgreSQL table
designed in `schema.sql`, unexecuted). Coverage reports observations inside planned windows per data origin and never
imputes a missing measurement. A planned day is the 24 h starting at the planned time; `window_days` widens it both
ways. Not yet in sync push/pull (schedules are created via the gateway API only) and no `recovery` sub-phase yet
(postflight only); both wait for the mission engine (M4).

## D-021 Risk engine scope: non-clinical rules only; RETURN_NOW is a human command (decided 2026-11-14, decision A)
The rule engine (M4) may evaluate only non-clinical conditions: device offline, data-quality states, missed scheduled
measurements, DONKI event notices, and statistical deviations labelled "for review". It never applies a clinical
threshold and never produces a health-risk label (rule 3 and D-004 unchanged). `RETURN_NOW` is a **human-issued command**
record carrying issuer, issue time, reason and mission context; MEDVITAL stores, syncs and displays it, never computes,
suggests, suppresses or overrides it, and no AI component can.

## D-022 Gemini boundary: simulated and public NASA data only (decided 2026-11-14, decision B)
Gemini is an explanation and reporting layer downstream of the deterministic analysis. Only simulated data and public
NASA data may be sent to it; no real astronaut health information or private medical records. Its output is a separate
`AIExplanation` record (never an observation) citing the records it describes; the backend must work when it is down.

## D-023 Cloud store: Cloudflare D1; SQLite authoritative per station; R2 for large artefacts (decided 2026-11-14, decision C)
Each station writes to its local SQLite first; that store is authoritative for the station. D1 is the cloud
synchronization store reached through a Worker implementing the existing sync contract. R2 holds source archives,
larger datasets and generated reports, never observations. PostgreSQL (D-006) remains a deferred future option.

## D-024 3D anatomical explorer deferred to M9 (decided 2026-11-14, decision D)
Deferred, not cancelled: it follows the three-station interfaces (M8). The Neuroglancer-inspired concept from the master
prompt (anatomical selection, layered overlays, timeline, data inspector with provenance; science computed only in
Python; licensed assets only) is preserved unchanged for that milestone.

## D-025 Observation `uncertainty` field; compatibility rules for additive schema changes (M3)
`HealthObservation.uncertainty`: optional standard uncertainty (1 σ) in the observation's own unit, ≥ 0, finite.
`None` = unknown and is never replaced by 0; an explicit 0 means known exact. Telemetry carries the same optional
extension field. The analysis engine reports how many analysed values have a known uncertainty and carries each value's
uncertainty onto deviations and flags; it never fabricates one.

Compatibility: the field is additive and optional, so `schema_version` stays 1 and every existing payload remains valid;
IndexedDB needs no migration (no new index). Stores now decide DUPLICATE vs CONFLICT by re-fingerprinting the *stored*
payload with the current model instead of trusting a fingerprint persisted by an older release. Without this, any
additive field with a default turned a legitimate retry of a pre-upgrade row into a false conflict (demonstrated on the
pre-M3 code for rows written before `quality`/`device_id` existed; regression test in `test_uncertainty_and_compat.py`).
Residual risk: an un-upgraded station rejects payloads containing the new key (`extra="forbid"`), so station-to-station
pushes omit `None`-valued fields, and stations should be upgraded together.

## D-026 Station-to-upstream delivery is a cursor over the local append-only log (M3)
`medvital/upstream.py`. Local SQLite stays authoritative (D-023). Upstream receives copies through the existing
`POST /sync/push` contract, so any MEDVITAL gateway (and later the Cloudflare Worker) can act as the upstream.

The outbox is not a second queue: pending means rows whose `server_seq` is above the destination's persisted cursor, so a
restart loses nothing. Mutation ids are uuid5(destination, observation id), so a retry (including one after a lost reply)
arrives as a duplicate, never a double.

Outcomes:
* accepted or duplicate: the cursor advances;
* upstream *rejection*: the item is appended to the `upstream_failures` audit table (append-only triggers) and skipped;
* batch-level 422: retried item by item to isolate the bad record;
* network error or 5xx: the cursor does not move;
* 401/403: delivery stops without advancing;
* a response missing results: protocol error, no advance.

Cursors are monotonic. Payloads omit `None` fields so older upstreams accept them.

Not yet:
* pulling from upstream (M6);
* an API/UI for delivery status (M6/M8);
* authentication (M5). The transport already accepts a bearer token, which is never logged.

## D-027 xAI Grok as an optional, advisory MCP reviewer for development (2026-11-14)
`tools/grok_mcp/server.py` exposes four explicit tools (`grok_review_code`, `grok_review_architecture`,
`grok_analyze_data`, `grok_research_review`) to Claude Code through a project-scoped `.mcp.json`. Claude stays the
primary model; `ANTHROPIC_BASE_URL` is untouched; Grok is called only when Claude chooses to, and its output is developer
advice, never a MEDVITAL observation, result or alert.

* **No new dependency.** Python standard library only: MCP over stdio as newline-delimited JSON-RPC, HTTPS via `urllib`.
  The trade-off is that we maintain the small protocol layer ourselves (tested end to end over real stdio).
* **API.** xAI Responses API (`POST https://api.x.ai/v1/responses`). The model defaults to `grok-4.7` and is
  configurable through `XAI_MODEL`. Both were taken from docs.x.ai on 2026-11-14.
* **Key.** Read only from `XAI_API_KEY`. It never appears in files, logs or responses. `.mcp.json` holds only the
  `${XAI_API_KEY}` placeholder, and an unexpanded placeholder is refused.
* **Data boundary (same principle as D-022).** Each call must declare a data classification (`source_code`,
  `architecture_or_docs`, `simulated_data` or `public_research_data`). Public data must cite its source. Content with
  measured-origin records or secret-like strings is refused before any network call. Requests set `store: false`.

## D-028 One generic append-only document store for non-observation records (backend M3)
Missions, published references, environmental events, source artifacts, RETURN_NOW commands and their status events,
rule findings and AI explanations are all immutable documents in one store: the `documents` table in SQLite, and the
same interface in memory. Each is keyed (kind, key) with an indexed `tag` and `sort_time`. The rules match
observations: append-only (enforced by triggers), idempotent by content fingerprint, re-fingerprinted with the current
model (D-025), and a conflict whenever the same key arrives with different content.

Each record type carries explicit marker fields:
* `EnvironmentalEvent.applies_to_individual=False`;
* `RuleFinding.clinical=False`;
* `AIExplanation.is_observation=False`;
* `ReturnNowCommand.issuer.issuer_type="human"`.

Command status is an append-only event history; the command record itself never changes. Every write goes through
`records_service.py`. An accepted-write audit (`write_audit`) records channel, client and device for each accepted
observation; rejections stay in the rejection log.

## D-029 Authorization policy now; Auth0 token validation blocked on dependency approval (backend M3)
`authz.py` defines the roles (astronaut, spacecraft_operator, ground_control, flight_surgeon, local_station), the
permission map, and the subject/mission scope rules:
* astronauts: their own subject;
* operators, ground control and flight surgeons: the crews of their assigned missions;
* local station: unrestricted.

RETURN_NOW may be issued only by an authorized *human*, in their own name, for an assigned mission. Routes resolve
authorization at the boundary and pass plain filters to processing code.

`MEDVITAL_AUTH_MODE=local` (the default) means trusted station LAN, so local monitoring never needs internet
authentication. `jwt` mode refuses to start: verifying Auth0 RS256 tokens needs a JWT library (e.g. `PyJWT[crypto]`),
which has not been approved (rule 7). We will not hand-roll JWT crypto. Write-path per-item subject scoping was added in D-032.

## D-030 Station-to-station replication of records reuses the sync pattern (backend M3)
* Observations: `/sync/push` and `/sync/pull` (unchanged).
* Documents: `/sync/documents/push` (validated per item through the same path as local writes) and
  `/sync/documents/pull` (cursor over `doc_seq`).
* Clients: `push_documents_upstream` (cursor `<dest>#documents`) and `pull_documents` (cursor `<source>#documents-pull`)
  share the outage, refusal and audit semantics of D-026.

Topology: astronaut → spacecraft → ground by push; ground → spacecraft by pull (e.g. a human-issued RETURN_NOW with its
status history). A replicated command keeps its original history; no second "issued" event is created. Not yet:
conflict-free handling when two stations change the *same* command's status concurrently. Both events are kept, and
order follows each station's feed.

## D-031 New metrics and wiring of the M1b calculations (backend M3)
New metrics:
* `bone.volumetric_bmd` (QCT, mg/cm3), separate from `bone.areal_bmd` (DXA, g/cm2): never pooled;
* `cardiovascular.stroke_volume` (mL, context `method`);
* `behavioral.time_in_bed` (h, **required** `tib_definition`).

Derived values (all `modeled`) come only from pairs with the same subject, origin, device, timestamp and context, at
`valid` quality. Ambiguous pairs are skipped and counted (`core/pairing.py`). The wired calculations are:
* MAP, labelled an uncited approximation;
* cardiac output;
* sleep efficiency, carrying `tib_definition`;
* BMD percent change with propagated uncertainty (`None` when unknown).

`DerivedValue` gains the optional fields `uncertainty` and `observed_at`.

Personal dose-rate series are integrated piecewise-constant over intervals ≤ 2× the median sampling interval. Longer
gaps are excluded and reported, so the result is a lower bound. This replaces the earlier "dose rates are never
summed" test wording: rates are still never summed, only integrated over time, and in dose units.

## D-032 Write authorization at every boundary; device ownership (security fix, backend M3)
**Vulnerability fixed.** A restricted principal could submit observations under another subject's or another device's
identity through `POST /observations`, `/sync/push` and `/telemetry`. Several reads were also unscoped: `/live`, the
rejection log, `/sync/pull`, schedules, and document pull.

**Fix:**
* **Ownership check.** `authz.observation_write_problem` requires every written observation's subject to be within the
  caller's scope (astronauts: only themselves). Any `device_id` must be *currently* assigned to that subject through an
  append-only `DeviceAssignment` record, where the latest assignment wins.
* **Where it runs.** Routes build an authorizer at the boundary. `ingest_observation` and `ingest_telemetry` apply it
  per item, so a failure is a logged per-item rejection, never a silent drop. Client-supplied subject, mission and
  device identifiers are checked against ownership and never override it.
* **Device assignments** need `write:records` plus mission scope, made in the caller's own name. The subject must be in
  that mission's crew.
* **Missions** can be created only within the caller's assigned missions, so creating one cannot grant new scope.
* **Station-only operations:** persisting simulations, and record replication (`/sync/documents/*`).
* **Other boundaries:** AI explanations must name the caller as `requested_by` and may cite only in-scope
  observations. Schedules, `/sync/pull`, `/live` and the rejection log are scoped or permissioned.
* **Astronauts gain `sync`** for their own-device outbox: every pushed item is checked, and every pull is limited to
  their own subject.

The local station principal (trusted LAN) is unrestricted, so offline local monitoring is unchanged. `jwt` mode still
fails closed. Regression tests: `tests/test_write_authorization.py` (17 tests).

## D-033 Spacecraft hub: one launcher, three apps, and an alert layer outside the modules (2026-11-14)
**Context.** The team plan needs RETURN_NOW / CHECK_VITALS / INFO alerts, a wearable simulator, a Cloudflare view and the
NASA link. P-2 noted that alerts conflict with rule 3 unless the rule is scoped explicitly.

**Decision.**
* `backend/medvital/hub/` is the spacecraft (Spot 2). It accepts the team plan's bursts, checks the wearable's device key,
  double-checks each burst (plausibility, glitch jump), stores it in its own SQLite file (`runtime/spacecraft.db`, the demo's
  "D1") and mirrors every value into the observation store as `simulated` telemetry (4 observations per burst). New metrics:
  `cardiovascular.spo2` (%), `radiation.dose_equivalent_rate` (uSv/h), `radiation.cumulative_dose_equivalent` (mSv).
* **Rule 3 is scoped, not removed.** The four modules stay threshold-free. Alerts live only in `hub/rules.py` and use
  either a cited NASA limit (NASA-STD-3001 Vol. 1: 600 mSv career [V1 4030], 250 mSv per solar particle event [V1 4031])
  or a value labelled `source="demo"` in `hub/settings.py` (spacewalk dose budget, heart-rate allowance above the
  astronaut's *own* baseline, SpO2 drop). Every alert is generated by fixed rules; AI only rewords it, and the onboard
  agent rejects any rewording that changes a number.
* The outbox uses the batch logic of the team's `spacecraft-sync/sync.js` (ported to `hub/service.py`; see D-035), and the
  NASA receiver (`nasa/app.py`) is unchanged in contract. `hub/verify` compares wearable sequence numbers, hub rows,
  observations, outbox and NASA's `/stats`.
* `start.py` (repo root) creates `.venv`, installs `backend[nasa]` and starts the NASA receiver and the hub; the hub
  serves the Astronaut, Cloudflare and 3D-body apps as static files. No build step.
* Optional AI: Workers AI through the Cloudflare REST API when `CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_API_TOKEN` are set;
  a local Ollama model for the onboard agent when `MEDVITAL_OLLAMA_MODEL` is set. Both fall back to templates/rules.
* Dependency: Flask (already used by `nasa/app.py`) is declared as the optional `nasa` extra. Chart.js 4.4.7 (MIT) is
  vendored in `nasa/vendor/` so the NASA screen works without internet.

**Data.** Scenario numbers are simulated. The normal dose rate (26.7 uSv/h) is Curiosity RAD's Mars-surface dose
equivalent, 0.64 mSv/day (Hassler et al., Science 2014). The replayed solar event is a real DONKI record
(2024-09-17T07:35:00-SEP-001); its dose spike in the demo is simulated.

## D-034 Mission simulation on real NASA data; one screen per role (2026-11-14)
**Context.** Feedback on the first build: the demo must show a whole mission day in about a minute, every screen
must always have live data, the astronaut's screen is the 3D body, NASA must be able to pick any astronaut, and
the data must come from OSDR, Curiosity RAD and DONKI "the way it's meant to be used".

**Decision.**
* **Demo clock.** One real minute = one mission day (`MEDVITAL_DAY_SECONDS`). Every wearable sends a burst every real
  second (= 24 mission minutes). Mission: cruise to Mars on days 1-8, landing on day 9 at 06:00, surface after.
* **The hub runs the crew.** `hub/simulator.py` drives all four wearables and the scheduled onboard tests from each
  astronaut's pre-flight report. Every value carries its origin: `simulated` (around the pre-flight value),
  `modeled` (bone density from the loss rates the 3D body already cites, Sibonga et al. 2015) or
  `pre-flight` / `entered`.
* **Curiosity RAD** (`data/nasa/rad_dose.csv`, from the PDS PPI RDR volume): the dose rate is a real RAD observation
  for that point of the mission (20 cruise days, 30 surface sols, tissue-equivalent detector E), times RAD's measured
  mean quality factor (3.82 cruise, 3.05 surface; Hassler et al. 2014). Medians check out against the papers
  (surface 0.209 mGy/day vs. 0.21 published). Demo factors on top: habitat shielding 0.8, SEP x40 outside.
* **DONKI** (`data/nasa/donki_2024-05-01_2024-06-29.json`): the 60 days May-June 2024 are replayed on the mission
  calendar (day 1 = 2024-05-01). M5+/X flares, fast CMEs, SEPs, storms and WSA-ENLIL CME arrival forecasts at Mars
  become upcoming events with their DONKI id and link. A real SEP window raises radiation and triggers RETURN_NOW
  for anyone outside: the May 2024 event falls on mission day 10, during the first spacewalk.
* **OSDR** (`data/nasa/osdr_studies.json`): the search API returns study metadata, not astronaut values, so MedVital
  links each health risk to the real OSDR studies (NASA view). No OSDR value is turned into a crew number.
* **Records to NASA.** Readings, tests, summaries, profiles and schedule events go in one batch at the end of each
  mission day; RETURN_NOW / CHECK_VITALS go at once (`outbox.urgent`). Scheduled blackouts (surface 02:00-04:30,
  one DSN gap in cruise) and the link switch hold the outbox; the batch goes when the link is back.
* **Screens.** Start page with three roles. Astronaut: log in or sign up (form and/or report upload; PDF text via
  `pypdf`), then the 3D body dashboard *is* the astronaut screen (`body-dashboard/public/hub-bridge.js`), with a
  hidden Demo drawer (key D). Hub: the private network with live devices, mission clock and the day-end send;
  clicking a box opens its details. NASA: crew picker, pre-flight report (PDF/text), pre-flight vs. in-flight table,
  mission chart, alerts, summaries, tests, upcoming events, OSDR studies.
* **Dependencies.** `pypdf` (pure Python) reads uploaded PDF reports. `reportlab` is only used by
  `tools/make_reports.py` to regenerate the sample PDFs; it is not a runtime dependency.
* **Cloudflare stays simulated** in this repository: no account, token or key is stored anywhere. Workers AI is used
  only when the presenter sets `CLOUDFLARE_ACCOUNT_ID` / `CLOUDFLARE_API_TOKEN` in their own shell.

## D-035 The link to Earth runs on Cloudflare: Worker + D1 + Workers AI, locked with a secret key (2026-11-14)
**Context.** The team plan puts the connection between the spacecraft and NASA on Cloudflare. The repository is public,
so nothing in it may let a stranger use the account (no account id used as a credential, no token, no key).

**Decision.**
* `cloudflare/` is one Worker (`medvital-link`) with a D1 database and the Workers AI binding. Routes: `POST /outbox`
  (the hub's batch; `INSERT OR IGNORE` by record id, answers the ids D1 holds, `503` while the link is down),
  `GET /pull?after=<seq>` (NASA's cursor), `GET|POST /link` (the link switch lives in D1), `GET /stats`, `POST /ai`
  (Workers AI, 30 calls/minute), `POST /reset` (`start.py --fresh`). `GET /health` is the only open route.
* **Lock.** Every other route needs `x-medvital-key`, compared in constant time with the `MEDVITAL_KEY` Worker
  secret. With no secret set the Worker refuses everything. The key reaches the laptops only through environment
  variables (`.env`, gitignored, or Codespaces secrets): `MEDVITAL_CLOUDFLARE_URL`, `MEDVITAL_CLOUDFLARE_KEY`.
* **Same guarantees as the direct link.** The hub deletes an outbox record only after the Worker confirms its id;
  NASA moves its cursor only after the records are in `mission.db`. Retries are harmless on both hops.
* **Fallback.** With the two variables unset, the hub sends straight to the NASA receiver as before (D-033), and
  the NASA receiver's `/batch` keeps working in Cloudflare mode too.
* **Workers AI through the binding**, so no Cloudflare API token sits on any laptop. Local `wrangler dev` has no
  Workers AI; the hub then keeps the rule text (the onboard agent's number check is unchanged).
* **No ids in config.** `wrangler.jsonc` names the D1 database but has no `database_id`: wrangler creates the database
  on the first deploy (from the dashboard's GitHub connection or the CLI), and the Worker creates its tables on first
  use. `migrations/0001_init.sql` documents the same schema.
* `spacecraft-sync/sync.js` is removed: its outbox logic lives in `hub/service.py`, its Cloudflare role in the Worker.
* Dependency: wrangler (dev only, through `npx`), needed only to run or deploy the Worker.

## D-036 Astronaut buttons, the Cloudflare checker, and the hub screen as a tree (2026-11-14)
**Context.** Feedback on v2: the astronaut needs Sleep, Leave the spacecraft (with a warning, then a forced return),
a bone-loss urine test and a mood check-in on the 3D page; Cloudflare must be used actively (checking connections and
the databases, feeding DONKI); cutting the link should break Cloudflare → NASA, with a visible 3 s retry; the hub
screen must read as a tree with one colour per kind of traffic.

**Decision.**
* **Link cut = Cloudflare → NASA.** `/outbox` always accepts; `/pull` answers 503 while the link is down and logs each
  refused attempt in D1 (`link_log`). NASA retries every 3 s (`MEDVITAL_RETRY_S`) and logs down / retry / restored in
  `mission.db`. Scheduled spacecraft blackouts still hold the hub's outbox. Without Cloudflare the old switch on the
  NASA receiver stays (D-033).
* **The checker runs in the Worker.** Cloudflare cannot call into a private laptop or Codespace, so the hub and NASA
  report in every 3 s (`POST /heartbeat`) with their counts and which parts answer. The Worker marks silent parts
  down, checks spacecraft-confirmed ≤ D1 and NASA + waiting = D1, and Workers AI words one sentence (numbers checked,
  at most once a minute, rule text otherwise). Without a Worker the hub runs the same comparison and labels it local.
* **DONKI through Cloudflare.** A cron trigger (every 30 min) fetches the last 30 days of FLR, CME, SEP, GST and IPS
  into D1; the hub reads `GET /donki`. Only flares carry a NASA-reported end time; nothing else gets a duration.
  The mission calendar still replays May–June 2024 (labelled as such); the live events are shown as "Live now".
* **Astronaut buttons** (`hub/actions.py`). Sleep overrides the plan until Wake up and logs `sleep.hours`. Leave the
  spacecraft: after 20 s a GO_INSIDE alert names the next real DONKI event within 12 mission hours (else a simulated
  "window closes") and a deadline that is never after that event; past it, RETURN_NOW (forced, full screen). An
  active RETURN_NOW always wins on the astronaut's screen. Time outside, dose (modeled) and minutes during a solar
  event are logged and sent to NASA. Mood 1–5 plus sleep vs. the astronaut's own pre-flight sleep: when both drift
  (demo limits in settings), CHECK_IN asks the flight surgeon to check in. No diagnosis wording.
* **Urine test for bone loss**: NASA's 24-h urine measures (NASA_SOURCES §8), stored as entered, no ranges.
* **Skip ahead** (demo drawer): jump to 2 h before the next solar event or to a mission day; no backfill.
* **Onboard agent**: Ollama (`MEDVITAL_OLLAMA_MODEL`, e.g. gemma4) → Workers AI through the Worker (rewording the
  rule answer, any changed number rejected) → rules. The hub screen draws the question's path.
* **Hub screen**: NASA above a Cloudflare box; inside it DONKI, the Worker + D1 and the checker; inside that the
  private network, the hub, the agent and every wearable. Six Okabe-Ito colours (readings, hub → Cloudflare,
  Cloudflare → NASA, checker, AI question, DONKI); red is reserved for "down".
* D1 writes: heartbeats are one upsert per part every 3 s (about 2,400 rows an hour while running).

## D-037 The new 3D dashboard, driven by the spacecraft; the onboard agent as a chatbot (2026-11-15)
**Context.** larsslt's dashboard update (v3.11 on `main`: 55 values, body labels, activity pill, body size, test
data with its own simulated stream) is the submitted astronaut screen. The onboard agent must chat like a chatbot.

**Decision.**
* `main` merged into the build branch; the dashboard is kept as written. Spacecraft mode adds five marked hooks in
  `app.js` (past-data label, Assistant to the onboard agent, Data input to the spacecraft, activity pill to the
  spacecraft) and `hub-bridge.js` switches the dashboard's own test stream off: the spacecraft is the one source.
* Values the spacecraft did not produce (blood panel, HRV, skin conductance, skin temperature, urine pH and citrate,
  and others) start from the dashboard's own invented "In range" set, labelled as test signals
  (`settings.DASHBOARD_TEST_SIGNALS`), and drift in the simulated blood draws. Yes/no findings default to "not reported".
* Activity: the spacecraft state sets the pill (asleep, resting, exercising, spacewalk); picking an activity in the
  pill acts like the astronaut's buttons. The hub screen shows the same activity in each astronaut's box.
* Chatbot (`hub/chat.py`): greetings, small talk, follow-ups with the last 8 turns, the astronaut's own numbers.
  Symptoms get the causes commonly reported in spaceflight with their source, a check of the live numbers, what to
  try, "not a diagnosis", and a **Send to flight surgeon** button. Only that button sends the chat to NASA
  (urgent record type `consult`, shown on the NASA page). Danger signs (general emergency warning signs, a
  convention) raise an urgent CHECK_VITALS alert at once. Order: Ollama (`MEDVITAL_OLLAMA_MODEL`, timeout
  `MEDVITAL_OLLAMA_TIMEOUT`, default 60 s), then Workers AI (small, fast model), then the built-in replies; any
  number a model states must appear in the astronaut's data.

## Open questions

* **Q-1 Offline computation parity.** Summaries are computed server-side only, so an offline client cannot show derived values. Options: port calculations to TypeScript with shared test vectors; run the Python in Pyodide/WASM; or cache the last server summary. Decide before building the dashboard.
* **Q-2 Real data.** Which NASA datasets are usable, redistributable, and match the metric set (NASA_SOURCES gaps)?
* **Q-3 Unit handling.** Only canonical units accepted. Is client-side conversion needed (e.g. µSv, bpm vs `{beats}/min`)?
* **Q-4 Mission time.** Observations use wall-clock UTC. Spacecraft/analogue contexts may need mission-elapsed time and clock-drift handling.
* **Q-5 Privacy.** IndexedDB is unencrypted at rest; health data on shared devices needs a threat model.
* **Q-6 Scientific review.** Metric set, summaries and caveats need review by domain experts before any public claim.
* **Q-7 `supersedes` semantics.** Query "current" view, handling of chains and out-of-order arrival.
* **Q-8 Service worker/PWA.** Data layer is offline-capable; app-shell caching is not built.
* **Q-9 Test dependency warning.** Starlette's TestClient emits a deprecation warning recommending `httpx2` over `httpx`; left on `httpx` (the documented dependency) pending review of the replacement package.
* **Q-10 Sync ordering under concurrent Postgres writers** (see ARCHITECTURE §5.4).
* **Q-11 Advanced analysis/AI engine.** Out of scope for v0.1; specify separately under the same provenance and no-diagnosis rules.

## Proposals (not accepted, not implemented) — 2026-11-14

### P-1 Telemetry contract in the master briefing vs. the current backend schema

Briefing contract: `event_id, device_id, crew_id, timestamp, domain, indicator, value, unit, source, quality, synthetic`.
Current schema: `core/schema.py` (`HealthObservation`). Nothing below has been changed; the team should decide.

| Briefing field | Current schema | Difference / proposal |
|---|---|---|
| `event_id` (`"EVT-000001"`) | `id` (UUID, client-generated) | Format differs. Sequential ids collide across devices; keep UUID, or accept `EVT-<device>-<seq>` only if uniqueness per device is guaranteed. Pick one. |
| `device_id` | none (only an optional `device` context key on some metrics) | **Missing.** Add a required `device_id` (first-class, not context) for wearable/gateway attribution and audit. |
| `crew_id` (`"CREW-001"`) | `subject_id` | Rename or alias. Current pattern already accepts `CREW-001`. |
| `timestamp` | `observed_at` and `recorded_at` | We keep two times (event vs. client record). Map `timestamp` → `observed_at`; keep `recorded_at`. Add plausibility bounds (reject far-future times) — currently only "timezone-aware" is checked. |
| `domain` | `module` | Same four values; rename or alias. |
| `indicator` (`"heart_rate"`) | `metric` (`"cardiovascular.resting_heart_rate"`) | Our ids are namespaced and more specific; briefing's `heart_rate` is not in the registry (nearest is *resting* HR, and a wearable stream is not resting-only). Needs a metric-catalogue decision. |
| `value` | `value` | Same (finite floats only). |
| `unit` (`"bpm"`) | `unit` (canonical `{beats}/min`) | **Example in the briefing would be rejected today** (`bpm` ≠ `{beats}/min`). Decide: change canonical unit to `bpm`, or add an alias table (Q-3). |
| `source` (`"simulated_sensor"`) | `provenance.source` + `provenance.data_origin` | The briefing's `source` mixes *what kind of thing* (simulated) with *which sensor*. Keep `data_origin` ∈ simulated/measured/modeled plus a free `source`. |
| `quality` (`"valid"`) | none | **Missing.** Add a `quality` enum (e.g. valid / suspect / invalid / unknown — values to be decided by the team) and make summaries exclude or flag non-valid points. Never silently drop invalid observations (briefing §8). |
| `synthetic` (bool) | derivable: `provenance.data_origin == simulated` | Keep derived (a stored boolean can contradict `data_origin`, and a bool cannot express measured vs modeled). Expose it in the API response for convenience. |

Related gaps against briefing §8 ("must not silently discard health observations"; "audit records"):
* **[Resolved in M3.2]** ~~Rejected observations are returned to the client but not stored server-side.~~ All write channels (`telemetry`, `api`, `sync`, `simulation`) now append rejections to the rejection log. There is no audit/quarantine table. Proposal: persist rejected payloads with reason, client/device id and time.
* Audit records for accepted writes (who/what/when, source device) do not exist beyond `received_at`.
* Retry, offline buffering, duplicate protection and conflict detection already exist (D-002, D-010).

### P-2 Briefing items that conflict with, or are not covered by, current rules

* **Alert levels (Normal/Watch/Warning/Critical)** vs. `CLAUDE.md` rule 3 and D-004 ("no risk labels, no clinical thresholds"). Resolvable only with sourced thresholds injected as cited reference objects, deterministic and AI-independent. **No NASA threshold has been read or verified yet (NASA_SOURCES §5).** Until then the system can only report statistical deviation from a personal baseline, labelled as such, or "insufficient data". If the team wants these labels, change rule 3 explicitly first.
* **Cloudflare stack:** settled for the link to Earth in D-035 (Worker + D1 + Workers AI). R2, Queues and Durable Objects are not used.
* **Twilio, Plotly, Service Workers**: not present; Plotly and Twilio would be new dependencies requiring a DECISIONS entry (rule 7). Twilio credentials must stay out of git.
* **Environmental vs. individual radiation** (briefing §5, module 1): DONKI events and Curiosity RAD are *environmental*; they should not be `HealthObservation`s for a subject. Proposal: a separate `EnvironmentalEvent`/`EnvironmentalMeasurement` entity with its own provenance, linked to subjects only by time window, never merged into individual exposure.
* **Four-laptop demo timestamps:** laptops need synchronised clocks (this laptop's Windows Time service was stopped when checked); see Q-4.
